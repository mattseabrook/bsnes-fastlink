Video driver (ruby/video/vulkan.cpp) — your code, real bugs
Fix 1 — Replace vkQueueWaitIdle with the fence you already signal.
In output() you have (line ~172):
cppif(flush) {
  vkQueueWaitIdle(_queue);   // full device-queue stall, heaviest possible sync
}
You already submit with _fences[imageIndex] (line 150) and wait on it at the top of the next frame (line 130). The vkQueueWaitIdle is redundant and it serializes CPU/GPU with zero overlap. Replace the body with a wait on only the just-submitted fence, or delete the block entirely:
cppif(flush) {
  vkWaitForFences(_device, 1, &_fences[imageIndex], VK_TRUE, UINT64_MAX);
}
This is your single highest-value change. vkQueueWaitIdle on the hot path every frame is what's burning your jitter headroom.
Fix 2 — Make flush actually optional instead of hardcoded true.
Line ~7 / member init: bool flush = true; //fastlink: default to GPU pipeline drain. Wire setFlush() to a config key so you can A/B it. Right now you can't measure its cost because it's always on. Default it false once Fix 1 lands — the per-image fence wait already bounds latency to one frame.
Fix 3 — Stop the unconditional break on Immediate mode; make present-mode a setting.
Lines ~497-501 force IMMEDIATE whenever available, which means permanent tearing and frame pacing dictated entirely by call cadence. Keep IMMEDIATE as an option, but let the user pick MAILBOX (tear-free, still low-latency) vs IMMEDIATE vs FIFO. For a speedrun where you want a clean image and predictable pacing, MAILBOX with a 2-3 image swapchain is usually the better consistency tradeoff than IMMEDIATE + queue-drain.
Fix 4 — Reconsider minImageCount forced to 2 alongside the drain.
Line ~488 forces minImages = 2. Two images + IMMEDIATE + vkQueueWaitIdle is a 1-frame-deep pipeline with no slack — on a noisy Windows box every DWM hiccup becomes a visible hitch. Once Fix 1 removes the full drain, 2-3 images lets the GPU overlap one frame of work without adding perceptible latency.

What run-ahead does: it doesn't alter game state, RNG, physics, or timing. The emulated SNES runs exactly as it always does. What it changes is when your input reaches the emulated console relative to the photons — it polls input later and rolls the internal processing-delay frames forward so the displayed frame reflects your press sooner. The game itself can't tell the difference; you're not getting extra frames of reaction time that a real console wouldn't give, you're getting back the latency the emulator added on top of original hardware. The RetroRGB high-speed-camera test is the usual framing: stock emulation sits a couple frames above real SNES latency, and run-ahead pulls it back toward—not below—the hardware baseline.
